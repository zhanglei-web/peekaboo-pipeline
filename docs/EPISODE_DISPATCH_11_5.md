# 11-5：Astra 后由每台 Qwen 独立处理整条数据

2026-11-05 更新。用户确认的分工是：预处理和 Astra 提供就绪数据；本机 Qwen 与远端 Qwen 动态领取不同数据，每台分别完成所领取数据的场景、事件、时序全部模型阶段。组装、校验、导出由协调器执行，不占模型请求槽位。

## 调度边界

```text
CPU 预处理 → GPU 深度 → 直接帧包 → Astra 筛选 → 公共就绪队列
                                             ├→ 本机：场景 → 事件 → 时序 ┐
                                             └→ 远端：场景 → 事件 → 时序 ┴→ 组装、校验、导出
```

各阶段保留独立请求、显式状态传递和回执，不合并成一个大请求，不依赖模型自动记忆。每个端点一次领取一条数据，优先完成已领取的数据；数据归属写入 `assignments/<episode>.json`，实际阶段配置写入 `episode_configs/<episode>.json`。失败或请求边界让出 GPU 后，恢复仍使用原端点，禁止静默转移至另一模型。

深度与本机 Qwen 继续互斥。远端不受本机模型加载/卸载影响。本机时序若超过 GPU 驻留预算，允许在请求边界保存并让出 GPU；该条归属不变。场景、事件、时序阶段的输出预算、图像、提示词、温度、seed、关闭思考设置及验证条件保持不变。

不生成 rosbag；中间帧包落盘，按条目交接。Astra 保持单路，本机和远端各一路。远端服务可提供两个请求槽位，此次管线仅使用其中一路；是否增加远端任务并发需依据实际吞吐和上游供给测试。

## 配置

在原配置上增加：

```json
"dispatch": {"mode": "episode", "endpoints": ["local", "lan"]}
```

未设置 `dispatch` 的旧配置仍采用阶段路由。整条模式的模型阶段实际路由来自所领取的端点，运行时不会使用旧的混合路由。为保持历史结果可审计，原 `routes` 字段仍保留在批次配置中；每条实际使用的路由以 `episode_configs` 和阶段回执中的 `dispatch` 为准。

整条模式要求所有启用端点均能承接场景 10000、事件 6144、时序 3072 token 的原输出预算，以及完整输入。2026-11-05 已确认远端服务有两个槽位，每槽位 16384 上下文；管线启动前核实远端公开容量不低于配置，实际多模态请求仍需服务端容量校验，不自动截断或缩减证据。

本批迁移计划将活跃条目上限由 4 改为 8、深度分组由 4 改为 2。40 GiB 活跃帧包、最低 8 GiB 可用内存及 20 GiB 剩余磁盘保护保留。扩大队列是为了增加可领取任务储备，并不保证两台机器始终满载；Astra 速度、失败重试和深度计算仍可能限制吞吐。

## 安全切换与恢复

1. 校验协调器 PID、创建时间、命令和排他锁，仅向协调器发出正常停止请求；等待其在途阶段或已发出的模型请求收尾，禁止杀子进程切换。
2. 迁移前确认旧协调器和阶段工作进程退出，逐项核对完成回执哈希、冻结依赖和输入身份。
3. 保存旧代码、旧清单、旧配置、状态快照及迁移审计，只允许显式列出的调度相关代码和配置差异。
4. 旧模式已经完整完成的数据列入绑定哈希的 `legacy_completed_episodes.json`，保留原产物和端点来源，不重跑、不改写为新调度产生的结果。未完成但已开始模型阶段的数据禁止自动转移，须先完成原路由或单独制定迁移。
5. 新模式从现有预处理/Astra 回执继续；完整验证还检查每条场景、事件、时序、组装回执的归属与阶段模型配置一致。
